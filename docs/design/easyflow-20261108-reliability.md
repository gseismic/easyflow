## 场景、接口边界与兼容性

按常见程度依次考虑：常规定时执行、故障后自动恢复、人工触发、重试后成功、按日期回补、清除失败任务后重跑、夏令时和跨时区运行。前四类维持原有默认调用；容量不足的回补返回未完成和待处理日期，CLI 退出非零并提示恢复方式，不要求调用方理解内部租约。

面向用户的 DAG、Operator 和 CLI 参数保持兼容；已存在数据库通过可选时区字段及默认值升级，旧时间数据按 UTC 解释，历史日志仍由数据库中的路径读取。回补结果新增带默认值的 `complete` 和 `pending` 字段，已有读取 `runs` 的调用方式保留；用户应检查 `complete` 和各运行状态。

内部契约：运行创建与容量判断在同一 SQLite 写事务；重复 scheduled 区间和不符合回补策略的区间使用可区分异常；容量不足可重试，租约丢失须停止调度。scheduler 会话负责取得、续租和释放资源，DagRun 执行锁退出进程后释放；任务重试时间和清除基线持久化，旧库升级时依据 clear 审计及尝试时间恢复基线。同步执行可能等待重试延迟，任务外部副作用仍需调用方保证幂等；对已有正在执行的外部调用，租约失效不保证撤销副作用。区间生成按请求范围线性增长，调用方应限制一次回补的日期范围。

## 方案比较与选择

### 时间与时区

- A：所有业务上下文都使用 UTC。实现简单，但改变传入的业务日期，不能表达非 UTC cron。
- B：UTC 作为比较和存储的标准，并持久化运行输入的时区信息，调度使用 DAG 开始时间的时区（没有开始时间时为 UTC），任务读取运行保存的数据区间。选择 B；手动运行无 DAG 时区时保留输入偏移，避免改变业务日期。固定时长从 DAG 开始时间或 UTC epoch 锚定；一次调度用稳定标识去重。

### 容量与回补

- A：先统计再插入，代码简单但存在竞争。
- B：在 SQLite 写事务中检查容量并插入，同时要求 DAG 上限和回补上限都成立。DAG 上限统计该 DAG 全部活跃运行，回补上限统计同一 backfill_id 的活跃运行。选择 B；容量不足的同步回补明确返回未完成，调用方可重试，不能报告成功。

### 恢复与租约

- A：在任务同步调用之间续租，长任务时租约会过期。
- B：独立续租并在租约丢失后阻止新任务和新运行；扫描时先推进已有活跃运行。选择 B。已有正在执行的外部调用不能安全撤销，仍依赖任务租约及外部幂等性。

同一 SQLite 实例内的手动、回补和 scheduler 可能同时尝试推进已有运行，因此按数据库路径、DAG 和 run_id 使用自动释放的本机进程锁（POSIX 文件锁或 Windows 字节范围锁）；未取得锁时保留现有状态，不能把竞争解释为失败。此方案适用于当前单机 SQLite 范围，不作为跨主机锁。

续租使用独立子进程，以免任务中的原生代码长期持有 Python GIL 时续租停顿；父进程退出时管道关闭，子进程随之停止续租。创建运行和领取任务还必须在写事务内验证租约归属和过期时间，以关闭检测与写入之间的竞争窗口。每次扫描使用唯一租约标识，即使用户给两个进程传入相同 owner 也不能共享租约。

调度用的 `now` 允许指定历史时刻，但租约始终使用真实时间；否则历史扫描会立即失去排他性。
常驻 scheduler 整个生命周期内持有同一租约，包含扫描间隔；单次扫描在结束时释放。
内部 `run_scheduler_once(use_lease=False)` 曾允许绕过独占性，现在会抛出明确错误；原参数仍保留，以便调用方迁移。

### 重试与等待

- A：进程内简单 sleep，重启后丢失重试时间和 clear 边界。
- B：持久化下一次重试时间及 clear 时的尝试基线，按状态事务判断；前序任务尚未完成时保留 DagRun 非终态并在后续扫描继续推进。选择 B。

## 查漏补缺

1. 时间边界使用实际时间比较，cron 跳过不存在的本地时间并以实际时间区分回拨时刻；已有 UTC 数据在没有时区元数据时按 UTC 解释。一次调度和 backfill 必须保证迭代终止。
2. 所有创建入口共享原子容量检查，clear 的检查和修改处于同一写事务；任务启动前再次验证代码版本，失败信息必须可通过日志查询。恢复与等待不能把正在执行的任务直接认定失败。
3. clear 使终态运行重新占用容量时，在同一事务检查该 DAG 的上限；DagRun 收尾在写事务中重新读取任务状态，不能使用 clear 之前的快照将运行错误地标为终态。
