# easyflow 第一版设计稿

日期：2026-07-02

状态：讨论稿

## 1. 背景

easyflow 目标是一个通用的轻量级 DAG 工作流引擎，金融量化数据生产是第一阶段重点验证场景之一。典型使用场景包括：

- 数据抓取：行情、复权因子、财务数据、指数成分、交易日历、公告新闻等。
- 指标计算：收益率、均线、波动率、行业中性化、横截面因子、多因子合成等。
- 回填修复：按交易日、标的范围、数据集切片进行补数、重算、失败重跑。
- 数据质量：对抓取和计算结果进行完整性、唯一性、缺失值、异常值检查。

easyflow 不以完全兼容 Airflow 或 Prefect 为目标，而是借鉴二者的有效设计：

- 借鉴 Airflow 的显式 DAG、任务状态、重跑、回填和可观测性。
- 借鉴 Prefect 的函数式接口、低样板代码和本地优先体验。
- 针对数据生产场景强化 Dataset、Slice、Calendar、Checkpoint、幂等任务和数据血缘。

## 2. 设计目标

第一版设计目标：

- 用户接口简单，主路径只需要 `@dag`、`@task`、`dataset`。
- DAG 结构在定义期显式构建，便于绘图、计划预览、恢复、重跑和影响分析。
- 任务定义和任务运行状态分离，避免状态污染任务模板。
- 数据集是一等概念，支持按交易日切片追踪数据生产状态。
- 大数据不通过任务返回值传递，业务数据读写由用户自己的代码负责。
- 数据依赖通过 `inputs` / `outputs` 自动生成 DAG 边，避免用户重复声明依赖。
- 纯控制依赖使用 `>>`，不引入 `wait_for` 作为主接口。
- easyflow 第一版只管理运行状态和 Dataset Slice 状态，不预设业务数据存储方案。
- DAG 支持 `schedule`、`start_date`、`catchup`、`tags` 等清晰运行元数据。
- 支持失败重试、超时、缓存、强制重建、失败重跑和区间回填。
- 支持业务日历，回填和窗口计算可以按交易日、自然日、工作日或自定义日历处理。

## 3. 非目标

第一版不做：

- 完整 Airflow 语法兼容。
- 完整 Prefect Future/State 编程模型。
- Web UI。
- 分布式 Worker。
- 多租户权限和团队治理。
- Kubernetes、Celery、Ray、Dask 等生产级执行后端。
- 动态任务映射高级语法。
- 复杂事件调度平台。
- 大对象结果传递。
- 通用业务数据存储抽象。
- 自动 `DataFrame` 读写协议。

这些能力可以作为后续扩展方向，但不进入第一版核心设计。

## 4. 设计方案比较

### 4.1 方案 A：Airflow 风格显式 Operator API

示例：

```python
with DAG("daily_factor") as dag:
    fetch = PythonOperator(task_id="fetch", python_callable=fetch_data)
    calc = PythonOperator(task_id="calc", python_callable=calc_factor)

    fetch >> calc
```

优点：

- DAG 显式，依赖图容易绘制。
- 与 Airflow 用户心智接近。
- 调度器实现直接。

缺点：

- 用户接口偏重。
- 容易暴露 Operator、TaskInstance、XCom 等框架内部概念。
- 对量化数据场景中的 Dataset、Slice、回填和数据版本表达不足。

### 4.2 方案 B：Prefect 风格隐式函数编排

示例：

```python
@flow
def daily_factor(symbols):
    for symbol in symbols:
        raw = fetch(symbol)
        calc(raw)
```

优点：

- 写法接近普通 Python。
- 条件、循环和动态逻辑自然。
- 本地调试体验好。

缺点：

- DAG 往往在运行时逐步生成，不利于运行前绘图和计划预览。
- 依赖图稳定性弱，不利于任务恢复、失败重启和影响分析。
- 容易退化成普通脚本加装饰器，缺少数据生产治理约束。

### 4.3 方案 C：函数式接口 + 显式静态 DAG + Dataset 感知

示例：

```python
daily_bar = dataset("market.daily_bar", slice_by="trade_date")
ma20 = dataset("factor.ma20", slice_by="trade_date")

@task(outputs=[daily_bar])
def fetch_daily_bar(trade_date: str):
    ...

@task(inputs=[daily_bar.window(20)], outputs=[ma20])
def calc_ma20(ctx, trade_date: str):
    ...

@dag(
    dag_id="daily_factor",
    schedule=None,
    start_date="2026-01-01",
    catchup=False,
    calendar="cn_stock",
    tags=["factor"],
)
def daily_factor(trade_date: str):
    fetch_daily_bar(trade_date)
    calc_ma20(trade_date)
```

优点：

- 用户接口接近函数式，样板代码少。
- DAG 在定义期显式构建，便于绘图、恢复和重跑。
- Dataset、Slice、Calendar 可以成为核心能力。
- 数据依赖只写一次：在 `@task(inputs=..., outputs=...)` 中声明。
- 窗口依赖在定义期可见，便于计划预览、血缘追踪和缓存判断。
- 适合数据抓取、数据加工和指标计算。

缺点：

- 需要限制运行时动态改变 DAG 结构。
- 用户需要理解 Dataset 和 Slice 的含义。
- 内部实现比纯任务调度器更复杂。

### 4.4 推荐方案

第一版采用方案 C。

核心原则：

```text
Prefect 风格的轻量函数 API，Airflow 风格的显式静态 DAG，数据生产场景的一等 Dataset。
```

## 5. 核心概念

### 5.1 用户概念

用户主要接触以下概念：

| 概念 | 含义 |
|---|---|
| DAG | 一个工作流定义，由多个任务和依赖组成 |
| Task | 一个可执行步骤，由 `@task` 装饰普通 Python 函数得到 |
| Dataset | 一个被任务生产或消费的数据产品的逻辑身份 |
| Slice | Dataset 的逻辑增量单位，例如某个 `trade_date` |
| Run | 一次 DAG 执行 |
| Context | 访问运行参数、解析 Slice、访问日历、记录日志和元数据的入口 |

不作为第一版主用户概念暴露：

- Operator
- XCom
- XComArg
- Future
- TaskInstance
- Executor
- Scheduler
- ResultBackend

这些属于内部实现或高级扩展点。

### 5.2 Dataset

`Dataset` 是数据产品的逻辑身份，不是 DataFrame，也不是具体数据库表。

示例：

```python
daily_bar = dataset(
    "market.daily_bar",
    slice_by="trade_date",
)
```

它表达：

- 这是什么数据。
- 这个数据是否按某个运行参数做逻辑切片管理。
- 哪些任务生产它。
- 哪些任务消费它。
- 某个 Slice 是否完成。
- 某个 Slice 由哪次运行、哪版代码、哪些上游数据生成。

Dataset 在 easyflow 中使用 `Dataset` 命名，而不使用 `Asset`。原因是金融领域中 asset 通常表示股票、债券、期货等金融资产，容易和数据资产概念冲突。

第一版 Dataset 不负责表达物理存储布局。具体数据存在 SQLite、Parquet、Postgres、iosql 或其他系统中，由用户自己的业务代码决定。

### 5.3 Slice

`Slice` 是 Dataset 的逻辑可追踪生产单位。

对量化日频数据，最常见 Slice 是：

```text
market.daily_bar[trade_date=2026-07-02]
factor.ma20[trade_date=2026-07-02]
```

`slice_by="trade_date"` 的含义是：

```text
easyflow 用 DAG run 的 trade_date 参数作为这个 Dataset 的逻辑切片键。
```

这不是物理存储分区声明。

特别说明：

- easyflow 用户接口中避免使用 `partition`。
- `partition` 这个词保留给物理存储层，例如 iosql 的物理分区。
- 后续接入 iosql 时，`DatasetSlice` 到 iosql `Partition` 的映射由 `IosqlStore` 处理，用户不需要感知。

绑定规则：

- `slice_by` 只绑定 DAG run params。
- 如果 `dataset(..., slice_by="trade_date")`，运行时必须提供 `trade_date`。
- 如果 DAG run params 缺少对应 key，构建执行计划时报错。
- easyflow 不从 task 参数名猜 Slice 值。

设计理由：

- Slice 是运行和状态管理维度，必须有稳定来源。
- 从 task 参数推断会在多任务、多别名、多日期参数时产生歧义。
- 绑定 DAG run params 可以让 `plan`、`backfill`、`status` 在任务执行前就确定目标 Slice。

未来可支持：

- 多 Slice 键，例如 `slice_by=["trade_date", "market"]`。
- 月度 Slice，例如 `slice_by="year_month"`。
- 不切片 Dataset，例如交易日历、静态行业分类。

第一版默认先支持单 Slice 键。

### 5.4 DAG

DAG 是静态依赖图。DAG 定义阶段调用 task 函数时，不执行真实业务逻辑，只创建任务节点。

允许：

```python
@dag
def pipeline(trade_date):
    extract(trade_date)
    transform(trade_date)
    load(trade_date)
```

任务之间的数据依赖由 `inputs` / `outputs` 自动生成。

纯控制依赖使用 `>>`：

```python
@dag
def pipeline(trade_date):
    ingest = fetch_daily_bar(trade_date)
    notify = send_notification(trade_date)
    ingest >> notify
```

第一版不鼓励：

```python
@dag
def pipeline(trade_date):
    if runtime_condition():
        task_a()
    else:
        task_b()
```

如果条件来自静态配置，可以允许；如果条件来自运行时数据，第一版暂不支持动态改变 DAG 结构。

### 5.5 外部输入 Dataset

一个 DAG 可以读取不由当前 DAG 生产的 Dataset。它们必须通过 `requires` 显式声明：

```python
@dag(
    dag_id="daily_factor_pipeline",
    requires=[daily_bar, adj_factor],
)
def daily_factor_pipeline(trade_date: str):
    ...
```

语义：

- `requires` 中的 Dataset 是当前 DAG 的外部输入。
- 运行前，easyflow 检查当前 Slice 是否存在 ready 版本。
- 缺失时，默认计划失败并给出明确错误。
- `requires` 只表达当前 DAG 的输入关系，不改变 Dataset 本身定义。

设计理由：

- 同一个 Dataset 在一个 DAG 中可能是输出，在另一个 DAG 中可能是输入，不能把 `external=True` 固化在 Dataset 定义上。
- 显式 `requires` 可以区分“外部依赖”和“漏写 producer”。
- 运行前检查外部输入是计划预览、恢复和失败诊断的基础。

## 6. 用户接口设计

### 6.1 Dataset 定义

```python
from easyflow import dataset

daily_bar = dataset(
    "market.daily_bar",
    slice_by="trade_date",
)
```

第一版参数建议：

```python
dataset(
    name: str,
    *,
    slice_by: str | None = None,
    description: str | None = None,
)
```

暂不把 `primary_key`、`schema`、`storage` 放入第一版主接口。原因：

- `primary_key` 和 `schema` 更接近数据质量或存储约束，第一版由用户业务存储或校验任务处理。
- `storage` 容易让 Dataset 过早绑定物理存储，第一版不提供通用 DataStore。
- Dataset 只负责依赖、血缘和 Slice 状态，不负责读写业务数据。

### 6.2 Task 定义

```python
from easyflow import task

@task(
    inputs=[daily_bar.window(20)],
    outputs=[ma20],
    retries=3,
    retry_delay="10s",
    timeout="10m",
)
def calc_ma20(ctx, trade_date: str):
    ...
```

常用参数：

| 参数 | 含义 |
|---|---|
| `inputs` | 任务声明依赖的数据集或数据集窗口 |
| `outputs` | 任务生产的数据集列表 |
| `retries` | 失败重试次数 |
| `retry_delay` | 重试间隔 |
| `timeout` | 超时时间 |
| `rate_limit` | 外部 API 限流 |
| `cache` | 是否允许命中缓存跳过执行 |
| `allow_partial` | 是否允许部分成功 |

默认策略：

- `retries=0`
- `cache=True`
- `allow_partial=False`
- `timeout=None`

`allow_partial=False` 是金融数据场景的安全默认值。抓取 5000 只股票失败 3 只时，默认整个 Slice 失败，不发布半成品。

第一版只保留 `outputs=[...]`，不提供 `output=...` 单数语法糖。

设计理由：

- `outputs=[...]` 和 `inputs=[...]` 形式一致，接口更明确。
- 第一版少做语法糖，避免 `output` / `outputs` 两套写法长期并存。
- 多输出虽然不是第一版重点，但内部和用户接口都不应把 TaskDef 写死为单输出。
- `outputs` 只声明任务成功后哪些 Dataset Slice 应标记为 ready，不代表 easyflow 会自动保存函数返回值。

第一版不支持字符串简写：

```python
@task(outputs=["market.daily_bar"])
def fetch_daily_bar(...):
    ...
```

设计理由：

- 字符串会丢失 `slice_by` 等 Dataset 元信息，除非引入全局 Dataset registry。
- 第一版先避免 registry 规则，要求用户传入 Dataset 对象，接口更明确。

### 6.3 DAG 定义

```python
from easyflow import dag

@dag(
    dag_id="daily_factor_pipeline",
    schedule=None,
    start_date="2026-01-01",
    catchup=False,
    calendar="cn_stock",
    tags=["factor"],
    concurrency=8,
    state_store="sqlite:///easyflow.db",
    requires=[daily_bar, adj_factor],
)
def daily_factor_pipeline(trade_date: str):
    ...
```

常用参数：

| 参数 | 含义 |
|---|---|
| `dag_id` | 工作流标识 |
| `schedule` | 自动调度规则，`None` 表示只手动触发 |
| `start_date` | 调度起始日期，设置 `schedule` 时建议显式提供 |
| `end_date` | 调度结束日期，可选 |
| `catchup` | 启用调度后是否补齐历史运行 |
| `calendar` | 业务日历，用于校验 Slice、生成回填日期和解析窗口 |
| `tags` | DAG 分类标签 |
| `concurrency` | 最大并发任务数 |
| `state_store` | 状态、运行记录、任务记录和版本元数据存储 |
| `requires` | 当前 DAG 依赖但不生产的外部 Dataset |
| `description` | 描述 |
| `default_task_args` | 默认任务参数 |

设计理由：

- `schedule`、`start_date`、`catchup`、`tags` 借鉴 Airflow 的清晰配置，降低迁移理解成本。
- `schedule` 只决定是否由调度器自动创建 DagRun；手动 `run` 不依赖它。
- `calendar` 不等同于 `schedule`，它决定哪些 Slice 合法，以及 `window(20)` 和 `backfill` 如何展开。
- `state_store` 只记录 easyflow 自身运行元数据，不负责业务数据读写。
- 第一版不提供 `data_store`，避免把 easyflow 设计成大而全的数据访问框架。
- 用户可以在任务函数中直接使用自己的 iosql、Parquet、数据库或 API client。

### 6.4 任务依赖

第一版只保留两类依赖表达。

数据依赖：

```python
@task(outputs=[daily_bar])
def fetch_daily_bar(ctx, trade_date):
    ...

@task(inputs=[daily_bar.window(20)], outputs=[ma20])
def calc_ma20(ctx, trade_date):
    ...
```

系统根据 `inputs` / `outputs` 在 DAG 定义期自动生成：

```text
fetch_daily_bar -> calc_ma20
```

纯控制依赖：

```python
a = prepare()
b = notify()
a >> b
```

原则：

- `inputs` / `outputs` 是主依赖接口。
- `>>` 只用于没有数据依赖的控制顺序。
- 第一版不把 `wait_for` 作为用户主接口。

Producer 唯一性规则：

```text
同一个 DAG 内，同一个 Dataset 只能由一个 task outputs 声明生产。
如果多个 task 生产同一个 Dataset，构建 DAG 时报错。
```

设计理由：

- 自动依赖图依赖 Dataset -> producer task 的唯一映射。
- 多生产者会导致下游依赖不确定，也会破坏 DatasetVersion 的生产者追踪。
- 如果业务上确实需要多个来源，应显式建中间 Dataset，再由合并任务产出最终 Dataset。

### 6.5 窗口依赖

指标计算常需要历史窗口。第一版窗口依赖只在 `inputs` 中声明：

```python
daily_bar_20d = daily_bar.window(20)


@task(inputs=[daily_bar_20d], outputs=[ma20])
def calc_ma20(ctx, trade_date):
    slices = ctx.slices(daily_bar_20d)
    dates = [item["trade_date"] for item in slices]
    bars = market_store.read_daily_bar(dates)
    result = compute_ma20(bars)
    factor_store.write_ma20(trade_date, result)
```

语义：

- `daily_bar.window(20)` 表示当前 Slice 需要读取截至当前交易日的过去 20 个交易日 Slice。
- `ctx.slices(daily_bar_20d)` 只返回需要的逻辑 Slice 列表，不读取业务数据。
- 业务数据由用户自己的 `market_store.read_daily_bar(...)` 读取。
- 不再同时提供 `lookback=20` 和 `ctx.read(..., window=20)` 两个事实来源。

设计理由：

- 窗口依赖必须在定义期可见，否则 `plan`、缓存、血缘和影响分析都无法准确判断。
- 如果 `lookback=20` 但任务内部读取 60 天数据，系统无法知道哪个才是真实依赖。
- 把窗口放在 `inputs` 中，能让用户只写一次依赖窗口。
- easyflow 不接管业务数据读取，避免第一版引入庞大的 DataStore 协议。

### 6.6 无 outputs task

任务可以没有 `outputs`：

```python
@task(inputs=[alpha_score])
def validate_alpha_score(ctx, trade_date: str):
    factor_df = factor_store.read_alpha_score(trade_date)
    validate_no_nan(factor_df, columns=["alpha_score"])
```

语义：

- 无 outputs task 只产生 TaskRun 状态，不产生 DatasetVersion。
- 无 outputs task 可以参与依赖图。
- 默认情况下，无 outputs task 失败会让 DagRun 失败，并阻止依赖它的下游任务执行。
- 无 outputs task 默认不参与 Dataset 缓存命中判断。

设计理由：

- 校验、通知、审计等任务天然不生产业务 Dataset。
- 强行要求它们写 Dataset 会增加用户负担，并制造无意义的数据产物。
- 保留 TaskRun 状态足以支持失败重跑和运行审计。

### 6.7 Context

任务函数第一个参数可以是 `ctx`。

```python
daily_bar_20d = daily_bar.window(20)


def calc_ma20(ctx, trade_date: str):
    slices = ctx.slices(daily_bar_20d)
    ctx.log.info("resolved %s slices", len(slices))
```

Context 提供：

| 方法或属性 | 含义 |
|---|---|
| `ctx.slice(dataset)` | 返回 Dataset 当前运行对应的逻辑 Slice |
| `ctx.slices(dataset_window)` | 返回 Dataset 窗口对应的逻辑 Slice 列表 |
| `ctx.calendar` | 当前 DAG 的业务日历 |
| `ctx.log` | 任务日志 |
| `ctx.run` | 当前运行信息 |
| `ctx.params` | 当前运行参数 |
| `ctx.record(dataset, **metadata)` | 可选记录输出元数据，例如行数、checksum、storage_uri |

当前 DAG run 有 `trade_date="2026-07-02"`，且 Dataset 声明了 `slice_by="trade_date"` 时：

```python
ctx.slice(daily_bar)
```

返回：

```python
{"trade_date": "2026-07-02"}
```

如果当前任务声明了：

```python
daily_bar_20d = daily_bar.window(20)


@task(inputs=[daily_bar_20d], outputs=[ma20])
```

则任务内：

```python
ctx.slices(daily_bar_20d)
```

返回的是窗口对应的 Slice 列表：

```text
[
  {"trade_date": "2026-06-05"},
  ...,
  {"trade_date": "2026-07-02"},
]
```

第一版不提供：

```text
ctx.read(...)
ctx.write(...)
ctx.vendor(...)
ctx.market(...)
```

设计理由：

- 第一版减少语法糖和框架魔法，业务数据怎么存由用户自己的代码决定。
- `Context` 只暴露调度器真正知道的信息，避免伪装成通用数据访问层。
- `ctx.record(...)` 是可选元数据记录，不影响数据依赖和任务成功判断。

### 6.8 低负担主路径

最小可用写法：

```python
daily_bar = dataset("market.daily_bar", slice_by="trade_date")
ma20 = dataset("factor.ma20", slice_by="trade_date")

@task(outputs=[daily_bar])
def fetch_daily_bar(trade_date):
    df = fetch_from_vendor(trade_date)
    market_store.write_daily_bar(trade_date, df)

daily_bar_20d = daily_bar.window(20)

@task(inputs=[daily_bar_20d], outputs=[ma20])
def calc_ma20(ctx, trade_date):
    dates = [item["trade_date"] for item in ctx.slices(daily_bar_20d)]
    bars = market_store.read_daily_bar(dates)
    factor_store.write_ma20(trade_date, compute_ma20(bars))

@dag(
    dag_id="daily_factor",
    schedule=None,
    start_date="2026-01-01",
    catchup=False,
    calendar="cn_stock",
)
def daily_factor(trade_date):
    fetch_daily_bar(trade_date)
    calc_ma20(trade_date)
```

这个例子中的用户概念只有：

- `dataset`
- `@task`
- `@dag`
- `ctx.slices`
- 用户自己的业务 store

## 7. 使用场景示例

### 7.1 数据抓取

```python
from easyflow import dag, task, dataset

from my_project import market_store, vendor
from my_project.quality import validate_no_duplicate_keys, validate_same_symbols


stock_universe = dataset("market.stock_universe", slice_by="trade_date")
daily_bar = dataset("market.daily_bar", slice_by="trade_date")
adj_factor = dataset("market.adj_factor", slice_by="trade_date")


@task(outputs=[stock_universe], retries=3, retry_delay="10s")
def build_stock_universe(trade_date: str, universe: str = "all"):
    symbols = market_store.resolve_symbols(universe, trade_date=trade_date)
    market_store.write_stock_universe(trade_date, symbols)


@task(
    inputs=[stock_universe],
    outputs=[daily_bar],
    retries=5,
    retry_delay="30s",
    timeout="10m",
    rate_limit="market_api:60/min",
)
def fetch_daily_bar(trade_date: str):
    symbols = market_store.read_stock_universe(trade_date)
    df = vendor.daily_bar(
        trade_date=trade_date,
        symbols=symbols,
    )
    market_store.write_daily_bar(trade_date, df)


@task(
    inputs=[stock_universe],
    outputs=[adj_factor],
    retries=5,
    retry_delay="30s",
    timeout="10m",
    rate_limit="market_api:60/min",
)
def fetch_adj_factor(trade_date: str):
    symbols = market_store.read_stock_universe(trade_date)
    df = vendor.adj_factor(
        trade_date=trade_date,
        symbols=symbols,
    )
    market_store.write_adj_factor(trade_date, df)


@task(inputs=[daily_bar, adj_factor])
def validate_market_data(trade_date: str):
    bars = market_store.read_daily_bar(trade_date)
    factors = market_store.read_adj_factor(trade_date)

@dag(
    dag_id="market_data_ingest",

    fetch_daily_bar(trade_date)
    fetch_adj_factor(trade_date)
    validate_market_data(trade_date)
```

系统根据 Dataset 依赖自动得到：

```text
build_stock_universe -> fetch_daily_bar
build_stock_universe -> fetch_adj_factor
fetch_daily_bar + fetch_adj_factor -> validate_market_data
```

运行：

```python
market_data_ingest.run(trade_date="2026-07-02", universe="all")
```

```python
market_data_ingest.run(
```

### 7.2 指标计算

```python
from easyflow import dag, task, dataset

from my_project import factor_store, market_store
from my_project.factors import (
    compute_adjusted_bar,
    compute_alpha_score,
    compute_ma20,
    compute_return_1d,
    compute_volatility_20,
)
from my_project.quality import validate_no_duplicate_keys, validate_no_nan


daily_bar = dataset("market.daily_bar", slice_by="trade_date")
adj_factor = dataset("market.adj_factor", slice_by="trade_date")
adjusted_bar = dataset("feature.adjusted_bar", slice_by="trade_date")
return_1d = dataset("factor.return_1d", slice_by="trade_date")
ma20 = dataset("factor.ma20", slice_by="trade_date")
volatility_20 = dataset("factor.volatility_20", slice_by="trade_date")
alpha_score = dataset("factor.alpha_score", slice_by="trade_date")


adjusted_bar_2d = adjusted_bar.window(2)
adjusted_bar_20d = adjusted_bar.window(20)
return_1d_20d = return_1d.window(20)


@task(inputs=[daily_bar, adj_factor], outputs=[adjusted_bar])
def calc_adjusted_bar(trade_date: str):
    bars = market_store.read_daily_bar(trade_date)
    factors = market_store.read_adj_factor(trade_date)
    out = compute_adjusted_bar(bars, factors)
    factor_store.write_adjusted_bar(trade_date, out)


@task(inputs=[adjusted_bar_2d], outputs=[return_1d])
def calc_return_1d(ctx, trade_date: str):
    dates = [item["trade_date"] for item in ctx.slices(adjusted_bar_2d)]
    bars = factor_store.read_adjusted_bar(dates)
    out = compute_return_1d(bars)
    factor_store.write_return_1d(trade_date, out)


@task(inputs=[adjusted_bar_20d], outputs=[ma20])
def calc_ma20(ctx, trade_date: str):
    dates = [item["trade_date"] for item in ctx.slices(adjusted_bar_20d)]
    bars = factor_store.read_adjusted_bar(dates)
    out = compute_ma20(bars)
    factor_store.write_ma20(trade_date, out)


@task(inputs=[return_1d_20d], outputs=[volatility_20])
def calc_volatility_20(ctx, trade_date: str):
    dates = [item["trade_date"] for item in ctx.slices(return_1d_20d)]
    returns = factor_store.read_return_1d(dates)
    out = compute_volatility_20(returns)
    factor_store.write_volatility_20(trade_date, out)


@task(inputs=[ma20, volatility_20], outputs=[alpha_score])
def calc_alpha_score(trade_date: str):
    ma = factor_store.read_ma20(trade_date)
    vol = factor_store.read_volatility_20(trade_date)
    out = compute_alpha_score(ma, vol)
    factor_store.write_alpha_score(trade_date, out)


@task(inputs=[alpha_score])
def validate_alpha_score(trade_date: str):
    factor_df = factor_store.read_alpha_score(trade_date)
    validate_no_nan(factor_df, columns=["alpha_score"])
    validate_no_duplicate_keys(factor_df, keys=["trade_date", "symbol"])


@dag(
    dag_id="daily_factor_pipeline",
    schedule=None,
    start_date="2026-01-01",
    catchup=False,
    calendar="cn_stock",
    tags=["factor"],
    concurrency=8,
    state_store="sqlite:///easyflow.db",
    requires=[daily_bar, adj_factor],
)
def daily_factor_pipeline(trade_date: str):
    calc_adjusted_bar(trade_date)
    calc_return_1d(trade_date)
    calc_ma20(trade_date)
    calc_volatility_20(trade_date)
    calc_alpha_score(trade_date)
    validate_alpha_score(trade_date)
```

系统根据 Dataset 依赖自动得到：

```text
daily_bar + adj_factor -> adjusted_bar
adjusted_bar(window=2) -> return_1d
adjusted_bar(window=20) -> ma20
return_1d(window=20) -> volatility_20
ma20 + volatility_20 -> alpha_score
alpha_score -> validate_alpha_score
```

`daily_bar` 和 `adj_factor` 由 `requires` 声明为外部输入。运行前，easyflow 会检查当前 `trade_date` 对应 Slice 是否 ready。

## 8. 运行接口

### 8.1 单日运行

```python
daily_factor_pipeline.run(trade_date="2026-07-02")
```

### 8.2 回填

```python
daily_factor_pipeline.backfill(start="2020-01-01", end="2026-07-02")
```

语义：

- 根据 `calendar` 生成交易日列表。
- 每个交易日形成一个或多个 DagRun。
- 已成功且缓存有效的 Slice 默认跳过。
- 失败 Slice 可以单独重跑。

### 8.3 计划预览

```python
daily_factor_pipeline.plan(trade_date="2026-07-02")
```

输出应包含：

- 会运行哪些任务。
- 会跳过哪些任务。
- 跳过原因。
- 哪些外部 Dataset Slice 必须 ready。
- 哪些 Dataset Slice 会被读取。
- 哪些 Dataset Slice 会被写入。
- 哪些任务会因为缓存命中而跳过。

### 8.4 失败重跑

```python
daily_factor_pipeline.rerun_failed()
```

语义：

- 只重跑最近一次失败的 TaskRun 或 Slice。
- 默认不重跑已成功且输入未变化的任务。
- 如果失败任务有下游任务，下游是否重跑由状态和数据版本决定。

### 8.5 强制重建

```python
daily_factor_pipeline.run(trade_date="2026-07-02", rebuild=True)
```

`rebuild=True` 是危险操作，含义是忽略缓存并重写目标 Slice。

设计理由：

- `refresh=True` 容易被理解为刷新状态或刷新读取缓存，不足以表达重写输出的风险。
- `rebuild=True` 更明确地表示重新构建本次运行会产出的 Dataset Slice。
- 后续如果需要更细粒度，可以增加 `rebuild=[ma20, alpha_score]`。

## 9. 内部运行时设计

### 9.1 内部对象

| 对象 | 职责 |
|---|---|
| `DagDef` | 静态 DAG 定义 |
| `TaskDef` | 静态任务定义 |
| `TaskNode` | DAG 中一次任务调用形成的节点 |
| `DatasetDef` | 数据集定义 |
| `DatasetInput` | Dataset 输入声明，可能包含窗口 |
| `DatasetSlice` | 某个 Dataset 的逻辑切片 |
| `DagRun` | 一次 DAG 运行 |
| `TaskRun` | 一次任务运行 |
| `DatasetVersion` | 某个 Dataset Slice 的一次成功产物版本 |
| `Scheduler` | 判断哪些 TaskRun 可以执行 |
| `Executor` | 执行 TaskRun |
| `StateStore` | 保存运行状态 |
| `ResultMetadata` | 可选保存任务返回摘要和用户记录的输出元数据 |

### 9.2 定义与运行状态分离

必须坚持：

```text
TaskDef 不保存运行状态。
TaskRun 保存运行状态。
DatasetDef 不保存 Slice 状态。
DatasetVersion 保存具体 Slice 产物状态。
```

这是 v1 原型需要修正的关键问题。否则恢复运行、失败重试、并发执行和状态查询都会变复杂。

### 9.3 TaskRun 唯一标识

建议 TaskRun 标识至少包含：

```text
dag_id
run_id
task_id
slice
params_hash
attempt
```

同时记录：

```text
code_hash
input_dataset_versions
output_dataset
state
started_at
finished_at
error
```

### 9.4 DatasetVersion

每次成功写入 Dataset Slice 后，记录一个 DatasetVersion：

```text
dataset_name
slice
version_id
producer_task_id
dag_id
run_id
code_hash
params_hash
input_versions
row_count
checksum
created_at
storage_uri(optional)
```

第一版可以先实现最小字段：

```text
dataset_name
slice
version_id
producer_task_id
run_id
state
created_at
metadata(optional)
```

## 10. 状态模型

第一版 TaskRun 状态：

| 状态 | 含义 |
|---|---|
| `pending` | 等待依赖满足 |
| `queued` | 已提交执行器 |
| `running` | 正在执行 |
| `success` | 成功 |
| `failed` | 失败 |
| `upstream_failed` | 上游失败导致不执行 |
| `skipped` | 被显式跳过 |
| `cached` | 缓存命中，未真实执行 |
| `retry_wait` | 等待重试 |

Dataset Slice 状态：

| 状态 | 含义 |
|---|---|
| `missing` | 没有成功产物 |
| `building` | 正在生产 |
| `ready` | 已成功生产 |
| `failed` | 最近一次生产失败 |
| `stale` | 上游或代码变化导致可能过期 |

无 outputs task 状态只记录在 TaskRun 中，不改变 Dataset Slice 状态。

## 11. 缓存与重建

缓存命中条件建议：

```text
task_id 相同
slice 相同
params_hash 相同
code_hash 相同
input_dataset_versions 相同
输出 DatasetVersion 存在且 ready
```

第一版可以先简化为：

```text
task_id + slice + params_hash + output ready
```

后续再引入 `code_hash` 和 `input_dataset_versions`。

`rebuild=True` 时跳过缓存检查并重建输出 Slice。

## 12. 业务数据写入边界

第一版 easyflow 不负责业务数据写入。

任务代码需要自己完成：

```text
1. 从外部 API、文件、数据库或自研存储读取数据。
2. 计算或校验数据。
3. 调用用户自己的业务 store 写入数据。
4. 写入成功后正常返回；写入失败时抛出异常。
```

easyflow 负责：

```text
1. 在任务执行前检查 inputs 对应的 Dataset Slice 状态。
2. 执行用户任务函数。
3. 任务成功后，把 outputs 对应的 Dataset Slice 标记为 ready。
4. 任务失败时，不标记 outputs ready，并记录 TaskRun failure。
```

设计理由：

- 第一版不强迫用户学习 easyflow DataStore 协议。
- 用户可以继续使用已有的 iosql、Parquet、数据库、对象存储或内部数据服务。
- easyflow 只记录“某个 Dataset Slice 已由某次 TaskRun 成功生产”，不假装知道数据物理写在哪里。
- 如果任务写入业务存储后又失败，easyflow 只能记录任务失败，不能自动回滚用户存储；这要求用户的业务写入尽量幂等。

推荐用户业务 store 采用类似语义：

```text
replace_slice(dataset, slice, data)
```

这不是 easyflow 第一版接口，只是对用户业务代码的建议。

## 16. 查漏补缺

### 16.1 第一轮：用户接口是否过重

风险：

- `Dataset`、`Slice`、`Context` 同时出现，可能让简单任务显得复杂。

处理：

- 简单任务允许不声明 Dataset。
- 第一版不支持字符串 Dataset 简写，避免引入全局 registry。
- 只有数据生产任务才需要 Dataset。
- 第一版不提供 `ctx.read` / `ctx.write`，用户继续使用自己的业务代码读写数据。
- 需要窗口日期时，通过 `ctx.slices(...)` 显式取得逻辑 Slice。

示例：

```python
@task
def notify():
    ...
```

### 16.2 第二轮：静态 DAG 是否限制过强

风险：

- 量化任务中可能需要按股票池动态展开任务。

处理：

- 第一版不支持动态任务图。
- 推荐任务内部批量处理 symbols。
- 后续再设计受控的 `map` 能力。

第一版推荐：

```python
fetch_daily_bar(trade_date, universe="all")
```

暂不推荐：

```python
for symbol in symbols:
    fetch_daily_bar(symbol)
```

### 16.3 第三轮：Dataset 是否绑定具体存储

风险：

- 如果 Dataset 过早绑定 SQLite、Parquet、iosql 或数据库表，会限制后续扩展。
- easyflow 中的逻辑 Slice 如果命名为 Partition，会和 iosql 的物理 Partition 冲突。

处理：

- Dataset 只表达逻辑身份。
- Slice 只表达逻辑运行和状态管理单位。
- 第一版没有 DataStore，具体读写由用户业务代码负责。
- 物理 partition 只出现在用户使用的存储层，例如 iosql。

### 16.4 第四轮：自动依赖是否隐藏太多

风险：

- 用户在 DAG 函数里只看到任务调用，看不到连边。
- 如果依赖完全由 Dataset 推导，错误的 `inputs` / `outputs` 会生成错误图。

处理：

- `plan()` 必须展示推导出的依赖图和原因。
- 构建 DAG 时检查外部输入、重复 producer 和孤立 Dataset。
- 文档明确数据依赖的唯一来源是 `inputs` / `outputs`。

## 17. 待确认问题

需要继续讨论：

- 第一版并发执行器选择线程还是进程。
- `ctx.record(dataset, **metadata)` 是否进入第一版，还是完全延后。
- `dataset(..., schema=...)` 是否进入第一版高级接口。
- 业务日历第一版是否内置 `cn_stock`，还是由用户注入。
- 缓存第一版是否记录 `code_hash`。
- 是否需要第一版支持 `shell` 任务。
- 多指标计算时是否需要批量声明因子依赖的便捷 DSL。

## 18. 初步结论

easyflow 第一版应定位为：

```text
通用轻量级、Dataset 感知、显式静态 DAG 工作流引擎；金融量化数据抓取与指标计算是第一阶段重点验证场景。
```

其核心不是复制 Airflow 或 Prefect，而是把以下能力组合成低负担用户接口：

- 函数式任务定义。
- 显式静态 DAG。
- 数据集 Slice 状态。
- 业务日历。
- 可恢复运行。
- 回填和失败重跑。
- 对用户幂等写入模式的明确约束。
- 数据血缘追踪。
