## 场景与边界

按用户目标和现有实现估算，常见场景依次包括：编写并测试 Python DAG；按时间自动执行；查看最近运行及失败原因；手动触发；暂停和恢复调度；重试或清除失败任务；查看任务依赖和日志；按业务日期回补。频率为设计估算，未经实际用户数据验证。

公共用户接口沿用 Airflow 3.2 已选子集的概念及支持范围内的参数、默认值、状态和副作用。内部存储、进程和租约机制不承诺 Airflow 结构兼容。低频能力可不支持，但应在合理边界明确失败；不接受参数后静默忽略。

## 核心设计决策

1. `default_args` 在构造任务时按“显式任务参数 > DAG 默认值 > 内置默认值”处理；无法支持的键明确拒绝。
2. 在受支持的可模板化 Operator 输入中统一查找和解析 XCom 引用，构建时建立依赖，执行时取得当前运行的值；传统 Operator 与 TaskFlow 共用处理规则。
3. 支持常见 Context 参数注入及最小任务实例操作；未实现的字段和方法不得伪装为已兼容。
4. `BashOperator` 的退出码、返回值和日志语义以所选 Airflow provider 兼容范围为准；日志流式写入，避免长任务无可读输出。
5. DAG 构造与发现支持常见的上下文和 `@dag` 自动注册；DAG 文件解析失败或超时不阻塞其他文件。子进程边界必须涵盖用户代码的实际导入，而非先做隔离检查后再在主进程重复导入。
6. 一个 scheduler 独立推进多个 DagRun，任务执行和重试等待不长期阻塞其他 DAG；跨入口并发容量在共享状态中按事务或等价机制维护。继续沿用 SQLite、单机进程和现有恢复约束。
7. 时间语义采用 Airflow 3.2 默认；现有 easyflow 数据库和旧版区间行为无需兼容或迁移。保留既有用户数据，开发和验证使用独立数据库。
8. 明确代码版本保护的边界。优先采用可验证的部署或项目源码版本标识；不能验证全部依赖时必须说明，不能宣称全代码已被冻结。
9. 触发、清理和回补明确展示副作用；回补提供 dry-run。暂停状态应持久化，重启后保持；运行中任务、已排队任务和手动触发的行为需明确。

### DAG 解析隔离方案

- 方案 A：先在子进程检查，再由 scheduler 在主进程重新导入。实现较少，但第二次导入仍可能阻塞或退出主进程，不能满足隔离要求，排除。
- 方案 B：解析子进程只输出调度必需的基础类型元数据，scheduler 使用该快照；任务在独立本地进程中重新导入并执行实际代码。该方案可隔离退出和超时，也不需要把用户函数反序列化到 scheduler；代价是需要明确快照字段，并在运行前校验定义版本。采用 B。
- 方案 C：把完整 Python DAG 对象序列化回 scheduler。虽能复用对象，但闭包、动态模块和反序列化会扩大依赖及执行边界，排除。

解析超时、进程退出和错误都应形成可查询的解析结果；单机进程隔离用于可靠性，不承诺对不可信代码提供安全沙箱。
常驻调度和管理界面采用按文件异步解析及短暂缓存；某个文件长时间导入时，已解析完成的其他 DAG 仍可展示和调度。变更的文件需重新解析，解析失败时不继续使用旧定义。
跨文件的重复 DAG ID 需要等相关文件解析完成才能发现；发现后停止调度冲突定义，较早已执行的运行无法撤回。为避免该窗口，部署前应使用一次性 `dags list` 检查重复 ID。

### 调度和容量

方案 A 让每个命令各自限制并发，代码少，但多个命令会突破实例上限。方案 B 使用 SQLite 保存实例级并发值，并在领取任务的写事务中统计所有运行中任务；显式配置可调整上限，降低上限时不终止已运行任务，只暂缓新任务。采用 B。

调度扫描独立推进不同 DAG；重试等待不占任务运行容量，也不阻止同一运行中的其他就绪任务。每个任务尝试结束后将状态持久化，后续扫描再决定是否重试。scheduler 的单次扫描可以等待所提交工作结束；常驻模式需要在已有任务运行时继续发现和调度其他 DAG。

### 本地代码版本边界

DAG 解析时记录 DAG 文件和可从其模块及任务函数追踪到的项目内 Python 模块内容哈希，创建运行和任务启动时重新校验。该机制可发现已导入本地模块的修改，但不覆盖运行期动态导入、第三方包、环境变量、外部文件或服务；用户需要在部署和任务层管理这些依赖，文档不能声称完整源码已被冻结。

### 默认时间语义

按照 [Airflow 3.2 的 trigger timetable](https://github.com/apache/airflow/blob/3.2.0/airflow-core/src/airflow/timetables/trigger.py)，cron 和 `timedelta` 默认产生零宽度数据区间：`logical_date == data_interval_start == data_interval_end == 本次触发时刻`。cron 对齐到时钟刻度；`timedelta` 的首次及错过调度处理遵循 trigger timetable，不再沿用旧版的区间结束后运行和 epoch 锚定默认。

`catchup=True` 从开始时间或上一自动运行继续补齐；`catchup=False` 跳过中间错过的时刻。必须持久化并读取上次自动运行，避免每次扫描都重复创建 `timedelta` 运行。业务若需要处理前一天等窗口，应在任务中明确计算，不能把零宽区间解释成前一个自然日。

## 界面结构草案

`[假设]` 面向单机用户，常见任务是快速发现失败、查看日志和恢复任务。用户已选择本机浏览器 Web，并确认下面的两层页面结构。

```text
DAG 列表：名称 | 暂停状态 | 调度 | 最近运行及结果 | 进入详情
  └─ DAG 详情：运行选择 | 任务依赖及状态 | 选中任务的日志/尝试
                次级操作：触发、暂停/恢复、预览并清理重跑、回补预览
```

列表主行动是进入详情；详情主行动是查看所选运行和任务。空目录、解析失败、scheduler 不可用、无运行、日志加载/失败、长名称和大量记录均需有明确状态。状态不能只靠颜色表示。用户已确认结构，可进入视觉实现。

实现采用 FastAPI 和组件化 React，界面只绑定本机地址；默认启动本机 scheduler，并可复用已经运行的 scheduler。页面从隔离解析得到 DAG 元数据，从 SQLite 查询运行历史和日志。手动触发只创建运行，由 scheduler 执行；暂停时可以创建手动运行，但要恢复后才会执行。正在执行的任务完成后暂停后续任务，恢复后继续。清理操作先展示将清理的任务并由用户提交，实际操作重新检查任务状态；回补预览同样只是快照，不承诺之后状态不变。

### 页面与状态

| 页面 | 首要信息及行动 | 次要信息和行动 |
| --- | --- | --- |
| DAG 列表 | 名称、调度、最近运行状态；选择 DAG | 调度器连接状态、解析错误、刷新 |
| DAG 详情 | 当前定义的依赖图、运行记录、所选任务日志 | 触发、暂停/恢复、预览清理、回补日期预览 |

列表区分加载、无 DAG、解析错误与调度器离线；详情区分无任务、无运行、无日志和日志读取失败。长 DAG 名称可换行，列表与依赖图可横向滚动；历史最多展示最近 100 次运行，日志最多展示末尾 1 MB。状态使用文字和颜色，不仅依赖颜色；交互控件提供可见焦点。界面文案的使用频率与目标用户仍属于场景 `[假设]`，尚无真实使用数据。

### 视觉规范

`[假设]` 采用浅色中性背景 `#f5f7f4`、白色内容面板、深绿主要操作 `#1c6748`，状态以绿、红、蓝、棕并配文字区分。面板圆角 12px、操作圆角 8px，间距以 8px 为主；普通操作最小高度 44px。宽屏将运行记录和日志并排，小屏改为纵向排列；依赖图保持可滚动，不隐藏任务。

`max_active_runs` 对普通 DagRun 和每个 backfill 分别计算，两者仍共同受实例任务并发限制。回补日期预览显示当前已有运行的状态和可否创建，实际创建时在事务中重新检查。

命令行采用 Typer 命令组；Python 核心调度和状态操作继续由既有服务函数负责，CLI 只处理输入、输出和退出码，不另建一套执行逻辑。

## 自查与开放问题

- 自动发现、解析隔离与运行进程都必须基于同一 DAG 定义来源，防止检查和执行版本不一致。
- 回补容量、正常调度容量与单机全局容量各自作用范围必须写清；外部副作用只按至少一次执行设计。
- 现有数据库不自动删除，新版不承诺兼容旧数据；时间语义变化在使用说明中明确。
- UI 需直接服务管理任务，不暴露租约或 SQLite 内部概念作为主要操作。
- 用户已确定可视化界面形式及时间语义，并确认页面结构。
