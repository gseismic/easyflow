## 风险、回滚和自查

SQLite 升级需兼容旧库；调度和重试时间变化会影响任务执行时点。完成标准是 30 项问题各有实现和针对性验证，完整测试通过。回滚时恢复本次代码和文档变更，保留用户数据及已有 `AGENTS.md` 修改；新增数据库列应保留以兼容历史运行。

实施前自查：容量检查覆盖全部创建入口；等待与租约丢失不能误判终态；原有 UTC 数据与历史日志仍需可读；夏令时按真实时间排序。

实施补充：为防止 scheduler 恢复时与手动触发或 backfill 的现有执行进程同时推进同一个 DagRun，增加本机进程级运行锁；进程退出后锁由操作系统释放，任务租约仍负责恢复已启动的尝试。

续租丢失与启动新任务之间还存在竞争，创建运行及领取任务时须在同一数据库写事务内校验当前 scheduler lease，避免旧 scheduler 越权继续推进。

代码自查补充：clear 已终态运行会重新占用容量，并可能与运行收尾交错；将容量检查、clear 与终态汇总分别纳入写事务，防止超限或把已清除的任务误报成功。

持续运行的 scheduler 在扫描间隔也持有并续租同一租约，确保整个常驻进程的独占性；单次扫描则在结束时释放。

兼容性复核补充：运行锁分别使用 POSIX 和 Windows 的本机文件锁，避免让纯 Python DAG 因 POSIX 专属模块无法导入；BashOperator 显式以 Bash 的 `-c` 参数执行。

原内部单次扫描允许用 `use_lease=False` 无条件绕过单 scheduler 保证；该参数继续接受，但显式拒绝禁用租约，常驻扫描改用持有会话的内部路径。

进一步复查：Python 原生扩展可能长时间持有 GIL，导致普通续租线程饿死。续租改为独立子进程，父进程退出后子进程通过管道关闭自动停止；增加持有 GIL 的长任务回归测试。

旧库升级时从 clear 审计记录恢复重试基线；没有可用审计信息但仍处于已清除状态的任务，以其现有 try_number 作为基线。
