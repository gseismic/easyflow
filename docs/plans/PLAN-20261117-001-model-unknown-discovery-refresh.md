## 目标、范围与约束

修复 Web 自动轮询或手动刷新后反复出现“部分工作流仍在解析或不可用，数量尚未完整”等提示。正常后台重解析已有当前文件快照时，继续提供完整结果和数量；首次发现、新增或修改文件尚未解析时仍提示加载，真实解析错误仍显示。

范围为 `src/easyflow/_internal/dag_parser.py` 中异步发现的完整性和等待判断、对应回归测试、现有版本声明及本次计划/结果/交接记录。沿用 FastAPI、React、uv、pnpm、pytest 与 playwright-cli；不新增依赖，不修改 SDK、业务 API 结构、数据库和前端布局，不调整 5 秒解析刷新周期，不修改 `GOAL.md`，不触发或更改业务任务与调度状态。

## 当前状态和依据

- `AsyncDagDiscovery.scan()` 对超过 5 秒的快照提交后台重解析，同时保留未变更文件的已有快照；返回的 `pending` 却直接取整个后台队列是否为空，将可用快照也判成未完成。
- `WebService.catalog()`、工作流与历史列表、两类 facets 共同使用 `discovered.pending`，分别导致 `loading`/`metadata_loading` 周期性变真和 `complete` 周期性变假。
- `web/src/components/WorkspaceNavigation.jsx` 根据 facets 的 `complete` 显示不完整提示；其他统计和列表加载提示受同一状态影响。前端正常展示服务端状态，不应直接隐藏真实不完整提示。
- 已读取 `docs/KNOWN-ISSUES.md`、`docs/TODOS.md`，没有该问题的现存条目；本次若完整解决则只在结果记录，不机械新增长期问题。
- CLI 调度循环使用发现结果的 sources/issues，不依据 `pending` 调度；本次不改变其提交规则。仍扩大执行异步发现与调度相关测试。

## 验证与完成标准

- 修复前回归能复现：源文件未变、已完整发现，超过 5 秒后即便来源及数量齐全仍返回 `pending=true`。
- 修复后同条件 `pending=false`，catalog/列表不退回加载，两类 facets 为 `complete=true` 且数量不变；后台解析本身继续运行，无额外阻塞等待。
- 首次、新增与修改文件没有对应快照时返回 `pending=true`；旧签名解析结果不能恢复成新文件的有效快照。没有 DAG 的成功解析也视为已完成。
- 文件解析失败时有明确 issues，facets 保持不完整；成功恢复后正确清除错误并恢复统计，不把错误变成永久加载。
- 实际浏览器跨自动刷新周期与手动刷新、页面重载后，不重复出现虚假的不完整提示；真实加载和错误仍可见。
- 相关必要测试与检查通过，记录实际命令和边界；未完成的验证不报告为通过。
